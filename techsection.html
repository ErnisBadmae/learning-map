Открытая адресация (CPython)

Всё в одной таблице. Ячейка занята → пробуем другую по псевдослучайной формуле i = 5·i + 1 + perturb, где perturb — старшие биты хеша.

«пёс» хотел в 3, там «кот» → проба увела в 0. Порог роста — 2/3 заполнения.

Компактный dict (с 3.6): разреженная таблица индексов + плотный массив записей в порядке вставки.
индексы (8 ячеек)1··0··2·

Отсюда: порядок вставки сохраняется (гарантия языка с 3.7), памяти меньше — пустые ячейки занимают байт индекса, а не три указателя.

Когда таблица растёт — замер sys.getsizeof на 3.14

Ключей стало611224386171
Ячеек было → стало8 → 1616 → 3232 → 6464 → 128128 → 256256 → 512

6-й ключ в 8 ячейках — это 6/8 > 2/3. Новый размер — степень двойки ≥ 3 × число ключей.

Вопрос Озона: «таблица на 100 ячеек, 100 элементов, что при 101-м?»
  1. Поправка: до 100 не дойдёт — рост начнётся при заполнении 2/3 (≈67) или 0,75 (75).
  2. Выделить таблицу больше (в разы), пересчитать позицию каждого ключа (hash % новый_размер) и переложить — O(n).
  3. Вставить новый ключ — O(1).
  4. «Скатится ли в линейную?» — нет: переезды при 6, 11, 22, 43… стоят в сумме ≈ 2n → амортизированно O(1). Если важна задержка каждой операции — заранее задать размер или переезжать постепенно (так делает Redis).

3. Строки и задача zero_one

Задача: "sunny string chapter" → строка из 0 и 1: 0 — символ встречается один раз, 1 — повторяется.

from collections import Counter

def zero_one(s):
    counts = Counter(s)                                          # шаг 1
    return "".join("1" if counts[c] > 1 else "0" for c in s)     # шаг 2

zero_one("sunny string chapter")   # '10110111101010000101'
ШагВремяПамятьПочему
1. Counter(s)O(n)O(k)k — разных символов (≤ алфавита); пробел тоже символ
2. генератор + поиск в dictO(n)O(1) на шагcounts[c] — O(1) в среднем
3. "".joinO(n)O(n)результат длины n, копируется один раз
ИтогоO(n)O(n + k)

Что спросят следом

ВопросОтвет
А если result += "0"?Строки неизменяемы → новая строка и копия на каждом шаге → O(n²) по языку. В CPython оптимизация на месте при единственной ссылке, но полагаться нельзя (PEP 8).
Что со старыми строками?Счётчик ссылок падает до 0 → память освобождается сразу. Последнюю держит переменная result. Циклический сборщик нужен только для циклов ссылок.
Сложность append?O(1) аморт.: список выделяет память с запасом.
Строка на 10 млрд символов?Асимптотика та же, ломается память: 10+ ГБ. Читать файл кусками, Counter.update(кусок); вторым проходом писать результат в файл.
Есть ли готовое?collections.Counter — подкласс dict, подсчёт на C, быстрее ручного цикла.
«Уникальные символы» — что уточнить?(а) все ли уникальны: len(set(s)) == len(s); (б) вернуть встречающиеся один раз: "".join(c for c, k in Counter(s).items() if k == 1) → "uyigchape". Регистр и пробелы — спросить.

12. Острова (N дней подряд) и медиана

Острова: у дней одной серии день − номер строки одинаков. Пользователь 2, оплаченные дни без дублей:
деньrnдень − rn
01-02101-01
01-05201-03
01-06301-03
01-07401-03
WITH days AS (SELECT DISTINCT user_id, order_date d
              FROM orders WHERE status = 'paid'),
g AS (SELECT user_id,
             d - ROW_NUMBER() OVER (PARTITION BY user_id
                                    ORDER BY d) * INTERVAL '1 day' AS island
      FROM days)
SELECT DISTINCT user_id FROM g
GROUP BY user_id, island HAVING COUNT(*) >= 3;

DISTINCT по дням обязателен: два заказа в один день сдвинут rn, и серия развалится. Самая длинная серия — MAX(COUNT(*)) по пользователю.

Строгая воронка и retention одной строкой 
-- воронка: группировка по пользователю снимает дубли
WITH f AS (
  SELECT user_id,
    MAX(CASE WHEN event_type='view'     THEN 1 ELSE 0 END) v,
    MAX(CASE WHEN event_type='cart'     THEN 1 ELSE 0 END) c,
    MAX(CASE WHEN event_type='purchase' THEN 1 ELSE 0 END) p
  FROM events GROUP BY user_id)
SELECT SUM(v), SUM(v*c), SUM(v*c*p) FROM f;
-- учебная база: 6, 3, 2
-- retention d1: EXISTS, а не JOIN — дубли не размножат
SELECT signup_date, COUNT(*) AS cohort,
  AVG(CASE WHEN EXISTS (
        SELECT 1 FROM events e
        WHERE e.user_id = u.user_id
          AND e.event_date = u.signup_date + 1)
      THEN 1.0 ELSE 0 END) AS d1
FROM users u GROUP BY signup_date;
-- 1.0 — чтобы не было целочисленного деления

13. Запрос медленный — что делаю

  1. EXPLAIN ANALYZE: полный скан вместо индекса? оценка строк сильно мимо факта? JOIN размножил строки?
  2. Функция над колонкой ломает индекс: WHERE date(ts) = '2026-01-02' → WHERE ts >= '2026-01-02' AND ts < '2026-01-03'.
  3. Индекс под фильтр и ключ JOIN; составной (a, b) работает слева направо — по одному b не поможет.
  4. 500 млн строк: партиционирование по дате, предагрегаты (витрина по дням), только нужные колонки.
  5. UNION убирает дубли (сортировка или хеш — дороже), UNION ALL — нет. По умолчанию UNION ALL.

RAG или файнтюнзнания меняются, нужны ссылки и права → RAG; стиль, формат, узкая задача → файнтюнпаттерны RAG: гибрид BM25 + dense, реранкер, переписывание запроса, small-to-big, фильтры по метаданным

17. Как оценить прогноз на 30 дней

Бэктест со скользящей точкой старта (rolling origin): обучили до даты → прогноз на горизонт → сдвинули старт → повторили.

обучениепрогноз (горизонт 5)не используется

Метрику считать по каждому горизонту h отдельно, усредняя по стартам. Пример (числа условные):

Горизонтh=1h=7h=14h=30одной цифрой
WAPE6%9%13%21%12% — прячет, что к 30-му дню всё плохо
Почему 30 точек ARIMA ≠ 30 строк бустинга
Это одна траектория из одной точки старта: точки коррелированы, ошибка растёт с горизонтом. Ряд нельзя делить случайно — только по времени.

Бустинг на рядах: стратегии многошагового прогноза

СтратегияКакПлюсМинус
Рекурсивнаяодна модель на t+1, прогноз подаём как лаг на следующий шагодна модельошибка копится по шагам
Прямая (direct)своя модель на каждый h: таргет сдвинут на h → «14 датасетов»нет накопления14 моделей; горизонты не согласованы
Горизонт как признакодна модель, h — колонка, строки размножены по hодна модель, данные общиедатасет в H раз больше
Multi-outputодна модель выдаёт вектор на H шаговсогласованностьне все бустинги умеют

Признаки: лаги таргета (≥ h для прямой стратегии!), скользящие со сдвигом (shift(h).rolling(7)), календарь, праздники, промо, известные заранее экзогенные. Бустинг не экстраполирует: предсказывает в диапазоне таргетов train → тренд моделировать отдельно или прогнозировать разности.

Заводы расширяются — дрейф известен заранее
  • Нормировать таргет: выпуск на единицу мощности → модель на стабильной величине → умножить на план мощности. План расширения — экзогенный признак.
  • Мониторинг: метрика по свежим фактам, ошибка со знаком (смещение), CUSUM; PSI признаков.
  • Регулярный сдвиг: коррекция остатка (сдвиг на скользящее среднее последних ошибок) + переобучение на скользящем окне с весом свежих данных; триггер — смещение вышло за порог.

Калибровка — решит ли проблему пограничных?

Модель говорит 0,9, а среди таких объектов позитивов 70% → переуверена. Калибровка на отложенной выборке: Platt (сигмоида поверх скора) или изотоническая регрессия. Проверка — reliability diagram, Brier, ECE.

Калибровка монотонна → порядок скоров тот же → AUC не меняется. Вероятности станут честными, порог осмысленным, но разделять классы лучше модель не начнёт.

Пограничные лечатся каскадом: зону неуверенности — в большую модель или человеку; маленькую дообучить на трудных примерах, найденных большой.
